# AirBeep 方案核查补充（2026-10-11）

本文补充 [技术方案与实施文档](AirBeep-技术方案与实施文档.md)，区分本机证据、公开资料和未验证的实机结果。它不代表已经在目标 iPhone 上完成安装、文件替换或通话测试。

## 当前判断

现有 Mac 环境下，**AirBeep 的 unsigned IPA 加免费 Apple ID 侧载，仍是较少新增构建依赖的候选路线**。但「IPA 符号完整」只证明构建产物包含预期函数，不能推出 iOS 27.0.1 上的配对、读写与静音效果已验证。目标设备尚未测试，因此不应把「技术上可行」写成定论。

| 路线 | 已查到的依据 | 当前限制 |
|---|---|---|
| AirBeep IPA | 本地 IPA SHA256 与原文档一致；[Sideloadly 官方页面](https://sideloadly.io/)称支持免费 Apple ID、Mac、拖入 IPA 安装 | Sideloadly 页面写 iOS 26+，没有针对 AirBeep + iOS 27.0.1 的实机成功证据；仍需解决 VPN、配对、读写可靠性 |
| Mac 端原版 airlift | [上游 README](https://github.com/0xjohnnydev/airlift)称无需 iPhone App | 上游 PoC 验证的是**新建文件**，不是覆盖现有提示音；当前 [Makefile](https://github.com/0xjohnnydev/airlift/blob/main/Makefile)依赖 `xcrun clang` 及系统私有框架；另有一份 [iOS 27.0 实机失败报告](https://github.com/0xjohnnydev/airlift/issues/4)，尚不能把它视为更短的可用路线 |
| Windows 版 AirliftSilence | [项目 README](https://github.com/YiHoooong/AirliftSilence)声称在 iOS 27.0.1 上完成读、替换和恢复，并提供无需 iPhone App 的 Windows GUI | 这是作者报告，未在目标设备复验；用户现有设备是 Mac，另需 Windows 环境和 Apple Mobile Device Support |

## 对原文档的必要修正

1. **免费签名的约束有官方依据。** [Apple Developer 帮助](https://developer.apple.com/help/account/basics/about-your-developer-account)明确说 Personal Team 的设备安装配置文件有效期为 7 天。[AltStore 文档](https://faq.altstore.io/altstore-classic/your-altstore)还说明其免费侧载流程最多同时有 3 个 App。这是账号/工具限制，不是 AirBeep 专属限制。Sideloadly 自己也确认免费 Apple ID 可用、有效期 7 天，但其网站宣传不能代替 iOS 27.0.1 实机验证。
2. **LocalDevVPN 不应写成绝对唯一组件。** 本地 `docs/reference/pinned_README.md` 的前提条件写的是 “LocalDevVPN / WireGuard”，即同类回环隧道在上游设计中可替代；是否满足 AirBeep 的具体连接地址仍未验证。[美国区 App Store 页面](https://apps.apple.com/us/app/localdevvpn/id6755608044)目前显示免费、版本 1.3.0，但评分会随地区和时间变化，不宜把原文档的 1.5 星当成稳定事实。中国区是否仍不可获取，本次无法直接复核。
3. **「备份不会丢」不成立。** `CallRecordingToneService.swift` 将备份写在应用的 Documents 目录；它不是独立于 App 的系统备份。重装或清除 App 数据后不能指望仍能从那里恢复。原文档说「实施前先手动抄一份备份」也有时间顺序错误：首次成功读取提示音之前，该目录没有 AirBeep 生成的备份。
4. **恢复状态可能误报。** `restoreSystemTone()` 在读取不到备份时直接将状态设成 `.systemTone`，没有先验证刚读出的系统提示音确为原音。因此备份丢失时，界面显示「已恢复」不能作为文件恢复证据。`refresh()` 在无缓存时也默认 `.systemTone`，只代表 UI 默认值。
5. **更改系统语言是作者声明的兜底办法，不是已验证恢复保证。** 证据仅见本仓库 `CHANGELOG.md`；缺少对目标设备的恢复前后文件比对。不能据此降低对原始音频独立备份的要求。
6. **法律结论需要收窄。** 原文档第五章记录了用户判断，但没有给出适用法域、通话对象位置及同意规则的法律来源。苹果的[官方说明](https://support.apple.com/en-euro/guide/personal-safety/ipsfa513e1a6/web)指出系统录音提示会让双方听到，并建议录音前取得明确同意。不要把「本人参与通话」概括为任何场景下都可无提示录音。
7. **读取也可能改变系统文件状态。** `docs/reference/airbeep.patch` 中的 `exploit_read_file` 会先将目标文件移到 Media，再读出并写回。补丁的错误分支明确承认恢复失败时移出的副本可能留在 Media。因而「先只读检查」也不是无副作用试运行。
8. **失败回滚仅是尽力尝试。** `CallRecordingToneService.swift` 在写入失败时用 `try? await writeTones(current, using: backend)` 回滚，回滚本身的失败不会向调用方单独报告；不能把「有回滚代码」等同于「失败后文件一定恢复」。

## 决策顺序

先确认目标设备的系统构建号和是否已有可用的独立原音备份，再按现有 Mac/免费账号条件评估安装成本。任何路线都应把「可安装」「可配对」「可读写」「备份可恢复」「实际通话效果」视为五个独立关口。没有目标设备的实测结果时，结论只能停在候选路线，不能宣布成功。避免在恢复证据缺失时修改系统提示音。

## 本次仍未查证

- AirBeep 与 Sideloadly 在 iOS 27.0.1 目标设备上是否能完成安装和启动。
- LocalDevVPN 或替代隧道是否能在目标设备上满足 AirBeep 所需连接。
- 目标设备的系统音频文件是否与静音资源时长、编码、读写预期一致。
- 修改后的实际通话行为，以及系统语言变更是否能可靠恢复文件。
- iOS 27.2 正式版和后续安全更新对该具体漏洞的影响。
