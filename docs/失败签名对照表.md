# 失败签名对照表

> 出问题时的第一手排查依据。**每一条都对照 `src/airlift.py` 的实际代码路径验证过。**
>
> 用法：出错后先在左列找到你看到的输出，然后**严格执行右列的动作**——尤其注意"目标是否已经空了"这一列，那决定你是否还有时间窗口。
>
> 排查的第一步永远是：**`python 设备体检.py scan`**（只读，不触发 exploit，跑多少次都安全）。

---

## 零、先理解一件事：read 和 replace 都不是只读操作

这是本方案最容易误解的地方。两个操作底层都是「**把目标文件移动到 Media → 再写东西回去**」：

| 操作 | 它做什么 | 读回失败时会发生什么 |
|---|---|---|
| `read` | 移到 Media → 读出 → **写回原位** | **目标变空**（原件留在 Media） |
| `replace` | 移到 Media → 读出 → **写入静音件** | **目标变成静音版**（原件留在 Media） |

**两者的目标路径都会短暂为空。** 区别在于失败后目标里剩下什么：

- `replace` 失败 → 目标里是**静音版**（虽然不是你想要的，但它是可用文件）
- `read` 失败 → 目标里**什么都没有**（CallServices 缺一个提示音文件）

**共同点：原件在两种情况下都会留在 Media 里，都可以用 `设备体检.py` 救回来。**

还有一个共同点：两个操作结束前都会 `_cleanup`，**只在成功拿到原件字节时才删除 Media 里的副本**——这个设计是对的，宁可留副本也不毁原件。

## 一、失败签名速查

### 🔴 目标路径变空了（最严重）

| 你会看到 | 目标是否为空 | 原件在哪 | **立刻做什么** |
|---|---|---|---|
| `{"ok": false, "error": "could not read /var/mobile/..."}` | ✅ **是** | Media 里的 `airlift-recovered-<token>` | 1. `python 设备体检.py scan`<br>2. 用 `pull` 抢救<br>3. 用 `airlift.py write` 写回原位 |
| 任何在 `read` 命令中途断连/报错后 | ✅ **是** | Media 里的 `airlift-recovered-<token>` | 同上 |

**为什么会这样**：`_read_file` 的写回步骤是

```python
finally:
    if result is not None:
        await _write_file(lockdown, apple, udid, ios_path, result)   # ← 没有 try 保护
    await _cleanup(afc, src, lnk, rec if result is not None else None, saved, saved_dirs)
```

如果 `_write_file` 抛异常，`finally` 会被中断，**`_cleanup` 不会执行**。此时原件停在 Media 的 `airlift-recovered-<token>`，目标路径是空的。**这是 `read` 操作真正的风险窗口。**

### 🟠 原件没读回来，但目标还有东西

| 你会看到 | 目标内容 | 原件在哪 | **立刻做什么** |
|---|---|---|---|
| JSON 里 `"previousSize": null` / `"backup": null` | 静音版（`replace` 已写入） | Media 里的 `airlift-replaced-<token>` | 1. `python 设备体检.py scan`<br>2. `pull` 抢救并核对 SHA256<br>3. 复制到 U 盘 |
| 日志：`Warning: could not read the old file back; leaving it at airlift-replaced-XXX in Media` | 同上 | 同上 | 同上 |

**这个情况比上面那条温和**：设备能正常用，只是你手上没有原件备份。但**原件的唯一副本就在 Media 里**，必须立刻抢救——工具的 `restore_sounds()` 因为没有本地备份会**拒绝执行**，GUI 里也没有翻找 Media 的入口。

### 🟡 还没开始搬文件就失败了（目标与原件都未受影响）

**这一整类的前提是：错误发生在 AirTraffic 开始搬运之前**（`_atc_sync` 之前，或 `_atc_sync` 本身失败因此根本没触发搬运）。此时**目标路径里原来的文件还在**，原件也还在原位，不需要救援。

> ⚠️ **唯一的例外见本节末**：`device rejected sync` 有一半情况发生在搬运之后。

| 你会看到 | 原因 | **做什么** |
|---|---|---|
| `iTunes not installed — need Apple Mobile Device Support DLLs` | 缺 `AirTrafficHost.dll` | 装 64 位 iTunes 或 Apple Mobile Device Support，重启电脑 |
| `no USB devices found` | 设备没被识别 | 数据线（要能传数据）/ 解锁 / 点「信任此电脑」/ 换 USB 口，别用 Hub |
| `no paired iPhone found` | ⚠️ **有两种原因，见下方专节** | 先按下方专节排查，不要盲目重插数据线 |
| `requested device not connected` | `--device` 指定的 UDID 不在线 | 去掉 `--device` 让它自动选 |
| `multiple devices; pass --device UDID` | 接了多台设备 | 加 `--device <UDID>`，或用 `设备体检.py` 时只留一台 |
| `zip extraction failed` | 上传的 zip 在设备侧解压失败 | 纯本地失败，重试；持续失败就比对静音件 SHA256 是否损坏 |
| `ATHostConnectionCreate failed` | 与 AirTraffic 建连失败 | 重启 Apple Mobile Device Service，或重插设备 |
| `staged assets not in device manifest` | 设备没接受 staged 资源 | 重试一次；持续失败说明协议被改 |
| `path must be absolute` | 路径没写全 | iOS 路径必须以 `/` 开头 |
| `path must be outside /var/mobile/Media` | 往 Media 里写了 | Media 归 AFC 管，用 `设备体检.py` 而不是 exploit |

### ⚠️ `device rejected sync` —— 唯一需要分情况判断的

这句话来自 `airlift.py:227`，是设备拒绝同步时的通用报错（设备侧日志对应 `SyncFailed {ErrorCode: 4}`）。它出现在**两个不同阶段**：

| 出现在 | 含义 | 目标是否受影响 |
|---|---|---|
| `RequestingSync` / `HostInfo` 阶段被拒 | 还没搬运，**安全** | ❌ 不受影响 |
| 已经发过 `FileComplete` 之后被拒 | 搬运可能已经开始 | ⚠️ **不确定，必须 `设备体检.py scan` 确认** |

**判断方法**：看日志里有没有出现 `Staged read request` / `Staged replacement` 以及 `Running AirTraffic sync...`。如果报错紧跟在 `Running AirTraffic sync...` 之后，就属于不确定的那种——**跑一次 `scan`**。

> **`ServiceProhibited` / `kAMDInvalidCheckinError` 不会出现在这个工具的报错里**——那是上游 airlift 走 RSD/`device_helper` 路径时的症状。如果出现类似的"服务被拒"，通常意味着 `com.apple.streaming_zip_conduit` 被设备拒绝，也就是 **iOS 27.2 beta 3+ 的特征，方案失效**。

### 🔴 `no paired iPhone found` —— 有两个完全不同的原因

**这个报错的名字具有误导性。** 它有两种成因，处理方式完全不同：

| 原因 | 怎么区分 | **做什么** |
|---|---|---|
| **A. 设备确实没配对** | `预检.bat` 第 4 项能看到设备；`设备体检.py` 能连上 | iPhone 上点「信任此电脑」 |
| **B. 工具的代码 bug**（更常见） | 设备明明连着、也信任了，就是报这个 | **用修补版 `airlift.py`**（见下） |

**原因 B 的技术细节**（已在本机用 pymobiledevice3 11.26.1 复现确认）：

`airlift.py:375` 有一行

```python
pt = ld.product_type or ""
```

但在 pymobiledevice3 **11.x 里 lockdown 客户端没有 `product_type` 这个属性**（`product_type` 只属于 irecv / DFU 恢复模式子系统）。所以这行抛 `AttributeError`，而它下面紧跟着

```python
except Exception:
    continue
```

**异常被静默吞掉，每一台设备都被跳过**，最后抛出与实际原因毫无关系的 `no paired iPhone found`。

更麻烦的是：两个仓库（`DahanGuy/airlift-windows` 与 `YiHoooong/AirliftSilence`）**都没有 pin pymobiledevice3 版本**，README 只写 `pip install pymobiledevice3`。该库在 PyPI 上已有 **700+ 个版本**，迭代极快，所以这个属性会随版本漂移——作者验证时是好的，你装到的版本未必。

**解决办法**：用修补过的源码。

```cmd
cd src
pip install pymobiledevice3

REM ❌ 不要直接用这个（有 bug）
REM python airlift.py ...

REM ✅ 用修补版
cd ..\source-patched
python airlift.py ...
```

修补版在 `artifacts/airliftsilence/source-patched/`，改动只有 `_resolve_device` 里的设备型号探测，改成「属性 → `all_values` → `get_value`」三级兜底，因此**新旧版本的 pymobiledevice3 都能工作**。补丁文件也留在同目录（`airlift-pymobiledevice3-compat.patch`）方便核对。

> **已经验证**：修补后，无论 lockdown 客户端有没有 `product_type`，都能正确解析出设备；非 iPhone 设备仍会被正确跳过。验证方法是用假的 lockdown 对象跑修补后的函数，并用 AST 确认再没有裸的属性访问。

## 二、判定"目标是否为空"的方法

`设备体检.py` 只覆盖 Media。要确认 CallServices 里的文件还在不在，有两条路：

### 方法 1：观察系统行为（零风险，推荐先做）

- 打一通电话**开始录音** → 听有没有提示音
- 如果**完全没有声音**：可能是静音版（正常），也可能是文件缺失（异常）——需要方法 2 或 3 才能区分
- **结束录音**再听一次

### 方法 2：用 `read` 探测（有风险，会把文件再移一次）

不推荐。这等于再冒一次上面第一条的风险。**只有在已经决定要重新替换时才用它。**

### 方法 3：直接重新 `replace`（其实是当时最省事的选择）

如果目标已经为空，`replace` 的流程会把"不存在的东西"当作旧文件处理：`previous` 会是 `None`（读不到），但**payload 仍会被写入目标路径**。也就是说：

> **在任何"目标为空"的故障状态下，再跑一次 `replace` 都能把文件恢复到可用状态（写入静音版）。**

所以最坏情况下你也不会陷入"无法把设备恢复成能用的样子"的困境。

## 三、救援标准流程（复制即用）

```cmd
REM 第 1 步：扫描（只读，安全）
python 设备体检.py scan

REM 第 2 步：从输出里找到 airlift-replaced-* 或 airlift-recovered-*，抢救出来
python 设备体检.py pull /var/mobile/Media/airlift-replaced-XXXXXXXXXX rescued.bin

REM 第 3 步：核对 SHA256 是否为原件
certutil -hashfile rescued.bin SHA256
REM   原件期望值（见附录）：
REM     StartDisclosureWithTone.m4a  e4ff9f8a0cfa1994321492c509bcd166e5ef6d341e9caa2b41631ef64eca3b47
REM     StopDisclosure.caf           6b9dd7f8a267a79b1ee2184e52d447c541f4bc76830424373a7bdf2fff9ef7be

REM 第 4 步：如果是原件，立刻复制到 U 盘！

REM 第 5 步：写回设备原位（此时目标路径是空的，write 正好适用）
python airlift.py write /var/mobile/Library/CallServices/Greetings/default/StopDisclosure.caf rescued.bin --logging
```

**判断抢救出来的是什么**：

| SHA256 匹配 | 含义 | 怎么做 |
|---|---|---|
| 匹配 `original-*` | ✅ 找回了原件 | 复制到 U 盘，写回设备 |
| 匹配 `silent-*` | 那是静音版，不是原件 | 继续找其他残留文件；原件可能已丢 |
| 都不匹配 | 可能是被 Apple 静默更新过的原件（作者承认发生过） | **保留它**，这是你唯一的原件；用它的格式时长重新生成静音件 |

## 五、如果实在救不回来

按严重程度从轻到重：

1. **文件缺失但流程还能跑** → 直接再跑一次 `replace` 写入静音版（见第二章方法 3）
2. **想恢复成原始提示音但没原件了** → 作者声称**更改系统语言**可强制系统重新生成默认提示音。⚠️ 此说法**仅见于 CHANGELOG，未经独立验证**，不要把它当保底手段
3. **同版本的另一台设备** → 用相同方式从那里 dump 一份原件（同一 iOS 构建号的音频资产应当一致）
4. 设备**不会变砖**。这套机制只移动和写入文件，不刷固件、不动系统分区。最坏结果是某个提示音缺失
